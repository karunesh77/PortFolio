JWT AUTHENTICATION — THE COMPLETE GUIDE FOR FULLSTACK DEVS

Karunesh Gupta • Oct 5, 2024

Every fullstack app needs authentication. Sessions were the old way — store a session ID on the server, send it as a cookie. JWT flips this: the token itself contains the user data, signed cryptographically so it can't be tampered with. The server doesn't need to store anything. This is what makes JWT perfect for stateless APIs and microservices.

HOW JWT WORKS — THE THREE PARTS

A JWT has three parts separated by dots: header.payload.signature. The header declares the algorithm (HS256 or RS256). The payload contains your claims — user ID, role, expiry time. The signature is a hash of header + payload using your secret key. Anyone can decode the header and payload (it's just Base64), but they can't modify it without invalidating the signature.

This is the key insight: JWTs are not encrypted, they're signed. Don't put sensitive data (passwords, credit cards) in the payload. Put just enough to identify the user — their ID, role, and email at most.

ACCESS TOKEN + REFRESH TOKEN PATTERN

A single long-lived token is a security risk — if stolen, the attacker has access for weeks. The solution is two tokens: a short-lived access token (15 minutes) and a long-lived refresh token (7 days).

The access token is sent with every API request in the Authorization header. When it expires, the client silently sends the refresh token to get a new access token. The user never notices — no login popup, no redirect. If the refresh token is also expired, then the user must log in again.

Why this works: even if an attacker steals the access token, they only have 15 minutes of access. The refresh token is stored in an HTTP-only cookie — JavaScript can't read it, so XSS attacks can't steal it.

THE EXPRESS MIDDLEWARE

On the backend, create an auth middleware that intercepts every protected request. It extracts the token from the Authorization header, verifies it using jsonwebtoken's verify method, and attaches the decoded user to the request object. If verification fails — expired, tampered, or missing — return a 401.

For role-based access, add a second middleware that checks req.user.role against the required role. Chain them: router.get('/admin/users', auth, authorize('admin'), getUsers). Clean, composable, and easy to test.

REACT AUTH CONTEXT

On the frontend, wrap your app in an AuthProvider that manages the auth state. On mount, it tries to refresh the token silently. If successful, the user is "logged in" without entering credentials. The context exposes login, logout, and the current user object to every component.

Protected routes check the auth context before rendering. If the user isn't authenticated, redirect to login. I use a ProtectedRoute component that wraps React Router's Route — clean and reusable across the app.

STORING TOKENS — THE RIGHT WAY

This is where most tutorials get it wrong. LocalStorage is accessible to JavaScript — any XSS vulnerability exposes your tokens. Cookies with httpOnly flag are better — JavaScript can't read them. But cookies are vulnerable to CSRF. The sweet spot: refresh token in an httpOnly, secure, SameSite cookie. Access token in memory (a JavaScript variable). On page refresh, use the refresh token to get a new access token.

Yes, the access token is lost on refresh. That's the point — it forces a refresh flow that validates the user is still legitimate. The UX cost is negligible — the refresh call takes 50-100ms.

COMMON PITFALLS

Don't use localStorage for tokens. Don't set token expiry to days or weeks. Don't skip HTTPS — tokens sent over HTTP can be intercepted. Don't forget to invalidate refresh tokens on logout — store them in a database and delete on logout. Don't put the JWT secret in your frontend code — it's called a secret for a reason.

JWT authentication is not inherently better or worse than sessions. It's a trade-off: statelessness and scalability vs. simplicity and revocation control. For SPAs with separate API backends, JWT wins. For traditional server-rendered apps, sessions might be simpler. Pick what fits your architecture.
