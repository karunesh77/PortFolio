DEPLOYING NODE.JS APPS ON AWS LAMBDA — A PRACTICAL GUIDE

Karunesh Gupta • Dec 28, 2024

Serverless is not just a buzzword — it fundamentally changes how you think about backend infrastructure. Instead of managing servers, patching OS updates, and worrying about scaling, you write functions and AWS handles the rest. I migrated parts of my backend to Lambda and this is what I learned.

WHY LAMBDA OVER EC2

Running an Express server on EC2 means you pay 24/7 whether or not anyone is using your app. With Lambda, you pay per invocation. For side projects and apps with variable traffic, this is a game-changer. My monthly AWS bill dropped from $15 to under $2 after moving background tasks to Lambda.

Lambda also auto-scales. If your endpoint suddenly gets 10,000 requests, AWS spins up more instances automatically. No load balancer configuration, no auto-scaling groups — it just works.

SETTING UP YOUR FIRST LAMBDA FUNCTION

The simplest approach is using the AWS Console, but for production you want Infrastructure as Code. I use the Serverless Framework — it lets you define your functions in a YAML file and deploy with a single command.

Your serverless.yml defines the function name, runtime (Node.js 18.x or 20.x), memory allocation, timeout, and the HTTP events that trigger it. Each function maps to an API Gateway endpoint. A POST to /api/users triggers your createUser function, a GET to /api/users/{id} triggers getUser.

The handler function receives an event object with the request body, path parameters, query strings, and headers. You process the request and return an object with statusCode, headers, and body. No Express, no middleware chain — just a function that takes input and returns output.

API GATEWAY CONFIGURATION

API Gateway sits in front of your Lambda functions and handles routing, CORS, rate limiting, and authentication. The REST API type gives you more control — you can set up request validation, response transformations, and usage plans.

CORS is the most common pain point. You need to handle it in two places: the API Gateway OPTIONS response and your Lambda function's response headers. Miss either one and your frontend gets the dreaded "CORS policy" error.

CONNECTING TO MONGODB

Lambda functions are stateless — they spin up, execute, and die. This means you can't maintain a persistent database connection like you do with Express. The trick is to cache the connection outside the handler function. AWS reuses the execution environment for subsequent invocations, so your cached connection persists across warm starts.

Use MongoDB Atlas with VPC peering for production. The free tier works fine for development, but for production workloads you want the connection to stay within AWS's network for latency and security.

CI/CD PIPELINE

I set up GitHub Actions to deploy automatically on push to main. The workflow installs dependencies, runs tests, and then uses the Serverless Framework to deploy. Environment variables (database URL, API keys) are stored as GitHub Secrets and passed to Lambda through the serverless.yml.

The deployment takes about 90 seconds — CloudFormation creates or updates the stack, packages the code, uploads to S3, and updates the Lambda functions. Zero downtime, every time.

COLD STARTS — THE REAL TALK

Cold starts are Lambda's biggest drawback. When a function hasn't been invoked for a while, AWS needs to spin up a new execution environment. For Node.js, this adds 200-500ms to the first request. For most APIs this is acceptable, but for user-facing endpoints where every millisecond counts, consider Provisioned Concurrency — it keeps a minimum number of instances warm.

Keep your deployment package small. Fewer dependencies mean faster cold starts. Use esbuild or webpack to bundle your code and tree-shake unused modules. My function packages went from 15MB to 2MB after bundling, and cold starts dropped by 40%.
