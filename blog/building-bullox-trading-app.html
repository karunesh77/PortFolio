BUILDING A REAL-TIME TRADING APP — THE BULLOX STORY

Karunesh Gupta • Nov 10, 2024

Trading apps live and die by speed. When prices change every second, your UI can't afford to lag. Bullox was my attempt at building a trading platform that feels instant — real-time price updates, instant alerts, and a portfolio tracker that reflects live market state.

THE REAL-TIME CHALLENGE

The core problem with trading apps is data flow. Market data changes constantly — you need to push updates to the client without the client polling every second. HTTP polling would work but it's wasteful. Long polling is better but still has overhead. WebSockets are the answer — a persistent bidirectional connection between client and server.

I used Socket.io on both ends. The server subscribes to market data feeds, processes the raw data, and emits formatted price updates to connected clients. Each client subscribes to specific symbols — if you're watching RELIANCE and TCS, you only get updates for those two. This keeps bandwidth usage sane.

FRONTEND ARCHITECTURE

React's reconciliation algorithm is perfect for trading UIs. When a price changes, only the affected DOM node re-renders — not the entire table. I used React.memo extensively to prevent unnecessary re-renders. The watchlist component renders 50+ rows and updating one row shouldn't trigger a repaint of the others.

State management was tricky. I went with useReducer + Context instead of Redux. The price state changes dozens of times per second — Redux's middleware chain adds overhead that's noticeable at this frequency. A bare useReducer dispatching directly is faster for high-frequency updates.

THE ALERT SYSTEM

Users set price alerts — "notify me when NIFTY crosses 22,000." These alerts are stored in MongoDB with the target price, direction (above/below), and notification preference. A background worker compares live prices against active alerts and triggers notifications when conditions are met.

The tricky part is deduplication. When NIFTY fluctuates around 22,000, you don't want to fire the alert 50 times. I implemented a cooldown period — once an alert fires, it enters a 5-minute cooldown before it can fire again. Simple but effective.

PORTFOLIO TRACKING

The portfolio view shows your holdings with live P&L calculations. Each holding stores the buy price and quantity. The current value is calculated in real-time by multiplying the live price with quantity. The total portfolio value updates every time any holding's price changes.

Charts use lightweight canvas rendering instead of SVG. For real-time price charts that update every second, SVG DOM manipulation becomes a bottleneck. Canvas draws directly to pixels — no DOM nodes to manage, no layout recalculations. The chart component receives new data points via WebSocket and appends them to the canvas buffer.

S3 FOR STATIC ASSETS

Company logos, chart thumbnails, and user avatars are stored on S3. I set up a CloudFront distribution in front of the bucket with aggressive caching — logos don't change often, so a 30-day cache-control header saves repeated S3 fetches. The frontend references CloudFront URLs, never S3 directly.

WHAT I'D DO DIFFERENTLY

If I rebuilt Bullox today, I'd use Redis for the real-time price cache instead of keeping it in Node.js memory. Redis Pub/Sub would let me horizontally scale the WebSocket servers — right now, all connected clients must be on the same server instance because price state is in-memory.

I'd also explore Server-Sent Events instead of WebSockets for the price feed. The data flow is mostly server-to-client (prices going out), and SSE is simpler to set up, auto-reconnects, and works through HTTP proxies without issues.
