SETTING UP CI/CD FOR NODE.JS WITH GITHUB ACTIONS

Karunesh Gupta • Sep 18, 2024

Manual deployments are a recipe for disaster. You forget to run tests, push untested code, and spend Friday night debugging production. CI/CD eliminates this entirely — every push triggers automated tests, and only passing code gets deployed. Here's how I set it up for my Node.js projects using GitHub Actions.

CI VS CD — THE DIFFERENCE

Continuous Integration (CI) means every code change is automatically tested. Push to a branch, tests run. Open a PR, tests run. This catches bugs before they reach main. Continuous Deployment (CD) takes it further — if tests pass, the code is automatically deployed to production. No manual steps, no human error.

You don't need both from day one. Start with CI (automated tests on every push), then add CD once you trust your test suite. A CI pipeline that catches 80% of bugs is infinitely better than no pipeline at all.

THE WORKFLOW FILE

GitHub Actions uses YAML files in .github/workflows/. Each file defines a workflow — a set of jobs triggered by events. The most common trigger is push to main or PR creation. Each job runs on a virtual machine (Ubuntu is fastest), installs your dependencies, and runs your scripts.

My standard workflow has three jobs: lint, test, and deploy. Lint and test run in parallel — no point waiting for tests to finish before checking code style. Deploy runs only if both pass and only on the main branch. This means PR branches get tested but never deployed.

CACHING NODE_MODULES

The biggest time sink in CI is npm install. A fresh install downloads hundreds of packages every run. GitHub Actions has a built-in cache action — it caches node_modules keyed by the hash of package-lock.json. If the lock file hasn't changed, it restores the cache instead of installing from scratch. This cut my CI time from 3 minutes to 45 seconds.

ENVIRONMENT VARIABLES & SECRETS

Never hardcode API keys, database URLs, or secrets in your workflow file. GitHub Secrets stores them encrypted — they're injected as environment variables at runtime. Go to Settings → Secrets → Actions, add your variables, and reference them as secrets.VARIABLE_NAME in the YAML.

For multi-environment setups (staging vs production), use GitHub Environments. Each environment has its own set of secrets. The staging workflow uses staging secrets, production uses production secrets. You can even add manual approval — the deploy to production waits for a team member to click "approve."

DEPLOYING TO VERCEL

For frontend apps, Vercel's GitHub integration handles CD automatically — connect your repo and every push to main triggers a deployment. No workflow file needed. But if you want custom logic (run tests first, then deploy), use the Vercel CLI in your GitHub Action. Install it, authenticate with a token from Secrets, and run vercel --prod.

DEPLOYING TO AWS

For backend APIs on EC2, the deploy job SSHs into the server, pulls the latest code, installs dependencies, and restarts the process manager (PM2). Store the SSH key as a GitHub Secret. Use the appleboy/ssh-action to execute remote commands without managing SSH connections yourself.

For Lambda deployments, use the Serverless Framework's deploy command in your workflow. It packages your code, uploads to S3, and updates the Lambda function — all in one command. The whole deploy takes about 90 seconds.

NOTIFICATIONS

A CI pipeline that fails silently is useless. I set up Slack notifications for failed builds — a webhook posts to a channel with the commit message, author, and a link to the failing run. For smaller projects, GitHub's built-in email notifications work fine. The goal is simple: you should know within minutes when something breaks.

Start small — a 10-line workflow that runs npm test on every push is worth more than a complex pipeline you never finish building. Iterate from there. Add linting next week, caching the week after, deployment when you're confident. CI/CD is a practice, not a one-time setup.
